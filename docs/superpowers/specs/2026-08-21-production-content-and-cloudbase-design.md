## 1. 阶段目标与硬边界

09B 负责把“候选素材”变成可审计的生产内容输入，并设计一条由 GitHub 到 CloudBase 的纯静态交付链路。项目方已作使用权与肖像许可声明：照片、视频、视频内音乐和字幕具有本项目公开展示使用权，照片中可辨识人物允许公开展示。该声明不等于景点归属、展品含义、人物身份或史实已经通过官方来源核验。本设计也不授权实施、上传或部署。

本阶段及后续实施必须保持以下边界：

- 网站仍为 React/Vite 纯静态单页应用；浏览器只读取构建产物、生产 JSON 和静态媒体。
- CloudBase 只使用静态网站托管和云存储；不创建或使用数据库、云函数、云托管容器、认证或服务端 API。
- `Videos/`、DOC/DOCX、XLSX 是原始交付归档和候选证据，不直接成为生产 URL，不提交大体积媒体。
- 不把候选文稿中的表述、测试 fixture、占位 URL 或人工未确认结果复制为“已审核”生产数据。
- 地图审图号、实际合规地图资源及完整疆域人工检查未完成前，`mapCompliance.status` 必须保持 `blocked`，GitHub 自动构建不得绕过 `npm run check:map`。
- 本设计阶段不上传、不部署、不转码，不创建、不修改、不删除任何 CloudBase 资源。

## 3. 方案比较与决定

### 3.1 方案 A：CloudBase 静态托管 + CloudBase 云存储（采用）

- CloudBase 静态托管连接 GitHub，安装依赖、执行发布门禁、构建 Vite，并只发布 `dist/`。
- 同一 CloudBase 环境的云存储承载 28 张照片、8 个 hero、8 条视频、8 个视频封面和 8 份 VTT。
- `src/data/sites.json` 在构建时固化为应用内容，媒体字段保存已人工核验的 CloudBase HTTPS/CDN URL。
- 浏览器不引入 CloudBase SDK，不登录、不调用数据库或函数，媒体按普通 HTTPS 静态资源加载。

采用理由：应用发布与大媒体生命周期解耦；Git 根路径部署不会覆盖媒体对象；视频不进入 Git；仍由一个 CloudBase 环境承担自动构建和静态媒体分发。

### 3.2 方案 B：应用与媒体全部放入静态托管根目录（不采用）

该方案看似简单，但 Git 根路径部署可能覆盖静态托管根目录中的已有文件，媒体与每次代码部署强耦合，大文件也会进入构建上下文。它不适合当前八条视频和独立审核/回滚需求。

### 3.3 方案 C：CloudBase 构建应用、外部 COS 托管媒体（不采用）

该方案技术上可行，但把权限、域名、缓存和回滚分散到两个产品边界，不满足本阶段让 CloudBase 同时承担自动构建和八馆媒体托管的优先目标。

## 4. 目标静态架构

```text
GitHub main
  └─ CloudBase 静态托管 Git 构建
       ├─ npm ci
       ├─ 内容门禁
       ├─ 地图门禁
       ├─ lint + unit tests + build
       └─ 发布 dist/（只有全部成功才替换候选部署）

浏览器
  ├─ HTTPS → CloudBase 静态托管：HTML / CSS / JS / 构建内 sites.json
  └─ HTTPS → 同环境 CloudBase 云存储/CDN：hero / photos / video / poster / VTT

不存在：数据库、云函数、云托管容器、运行时内容 API、用户上传接口
```

CloudBase 官方文档当前说明静态托管支持 Git 仓库部署、自定义安装/构建命令、`dist` 输出、HTTPS 与 CDN；云存储支持图片、文档和音视频等非结构化文件。能力依据：

- [CloudBase 静态托管快速开始](https://docs.cloudbase.net/hosting/quick-start)
- [CloudBase 静态托管部署方式](https://docs.cloudbase.net/hosting/web-hosting)
- [CloudBase 产品能力概述](https://cloud.tencent.com/document/product/876/18431)

当前会话未暴露 CloudBase MCP，因而尚未实时核验 `red-footprint-preview-d5322636bd` 的地域、套餐、容量、静态托管实例、云存储桶、默认域名、GitHub 绑定或权限状态。后续实施只能先做 MCP 只读盘点；任何创建、绑定、上传、部署或配置修改都必须等待单独人工授权。

## 5. CloudBase 交付契约

### 5.1 GitHub 自动构建

后续经授权配置时采用：

- 仓库分支：`main`；
- Node.js：选择与项目 `engines`/CI 锁定版本一致的 CloudBase 可用版本；
- 安装命令：`npm ci`；
- 构建命令：使用仓库内唯一的发布验证命令，不直接使用裸 `vite build`；
- 输出目录：`dist`；
- 部署路径：`/`；
- 触发条件：只有生产内容、媒体和地图均满足门禁后，才授权连接和启用自动部署。

发布命令必须按确定性顺序执行内容检查、地图检查、lint、单元测试和构建。任何一步非零即终止，不上传半成品。不得增加 `--skip`、环境变量后门、预览专用成功开关或忽略退出码的 shell 逻辑。

由于地图当前为 `blocked`，即使未来先写好构建配置，当前提交也必须安全失败并保持未发布；不能为了获得绿色 CloudBase 构建而临时移除地图门禁。

### 5.2 静态媒体托管

媒体对象使用不可变英文路径。建议对象前缀：

```text
media/sites/<site-id>/v1/hero/<site-id>-hero.webp
media/sites/<site-id>/v1/photos/<site-id>-photo-01.webp
media/sites/<site-id>/v1/video/<site-id>-video.mp4
media/sites/<site-id>/v1/poster/<site-id>-video-poster.webp
media/sites/<site-id>/v1/captions/<site-id>-captions.vtt
```

规则：

- 目录与文件名只使用小写英文、数字和连字符；不使用中文、空格、原始哈希名或日期型临时文件名。
- 每次正式替换使用新版本前缀（如 `v2`），不原位覆盖已发布对象。
- `sites.json` 只保存最终 HTTPS URL；不得保存 `cloud://`、本机路径、临时签名 URL、HTTP URL或占位域名。
- 生产 URL 的主机必须来自对目标环境只读盘点后确认的 CloudBase 静态资源/CDN 域名；设计阶段不虚构域名。
- 图片、封面和 VTT 可公开读取；视频按静态播放所需范围配置。权限和防盗链由负责人结合微信/Safari/Chrome 播放验证后人工确认。
- 代码构建不上传媒体；媒体上传是独立、受授权、带清单和摘要复核的发布动作。

### 5.3 缓存与版本回滚

- Vite 哈希 JS/CSS 使用长期 immutable 缓存；HTML 使用短缓存。
- 媒体对象因路径带版本号，可使用长期缓存；`sites.json` 切换到新 URL 后再清理旧版本。
- 回滚应用：选择上一个通过门禁的 Git 提交/CloudBase 部署记录。
- 回滚内容：恢复上一个通过审核的 `sites.json` 提交。
- 回滚媒体：把 `sites.json` URL 恢复到上一版本前缀，不覆盖或删除旧对象。
- 删除旧媒体是发布稳定后的独立人工授权动作，不属于自动构建。

## 7. 正式内容核验与生产数据

### 7.1 逐事实来源台账

每个地点先建立事实台账，再写正式正文。每条来源至少记录：

- 来源 ID、来源类型；
- 页面/文献标题；
- 发布机构；
- 精确 HTTPS URL；
- 访问或现场取证日期；
- 支持的字段路径；
- 必要的快照、展板照片或档案位置；
- 核验人和核验结论。

至少覆盖 `officialName`、简称、省市区、两类地址、坐标与坐标系、开放时间、预约规则、参观提示、官方称号、历史、人物、精神和媒体说明。一个“官网首页”链接不能笼统支持所有模块；每个事实模块必须至少有一条明确、权威、可追溯的来源。

### 7.2 正式正文流程

每馆依次完成：

1. 把候选 DOC/DOCX 拆成原子事实与团队观点；
2. 为每个事实绑定权威来源，标记冲突、时效和待确认项；
3. 重新撰写基础信息、历史、人物、精神和寻访感悟；
4. 把事实陈述与团队感悟分开，感悟不得引入新的未核验史实；
5. 内容审核人逐馆签字，生成独立 `contentReview`；
6. 只有八馆全部为 `verified` 后，才生成生产 `src/data/sites.json`。

开放时间、预约规则与参观提示具有时效性，必须保存核验日期，并在公开发布前再次复核。候选文稿中出现的正式名称、人物、年代、场馆称号和开放信息不因“看起来合理”而自动通过。

### 7.3 生产 `sites.json` 契约

生产数据源固定为 `src/data/sites.json`，恰好八条，使用本设计的稳定 `site-id` 和正式名称。建议在现有模型上补足：

- `coordinateSystem: "GCJ-02"`；
- `markerAddress` 与页面 `address`；
- 完整来源元数据及 `supports` 字段映射；
- `contentReview`；
- 项目方媒体使用权与照片人物肖像许可声明记录；
- 视频封面披露与接受记录；
- 媒体对象摘要/版本清单的引用。

`sites.json` 是构建时生产输入，不是在线 CMS。不得包含 fixture、`example.test`、`.invalid`、localhost、占位文本、合成路径、临时签名 URL或硬编码审核成功状态。AI 水印封面可以按项目方决定进入生产，但必须透明记录水印存在及接受信息，不得伪装成无水印素材。

雨花台、江上青和扬州现有水印封面的生产记录至少包含：

```json
{
  "aiWatermarkPresent": true,
  "aiWatermarkAccepted": true,
  "acceptedBy": "项目方",
  "acceptedAt": "2026-08-21"
}
```

内容门禁不得要求 `aiWatermarkPresent` 为 `false`。当其为 `true` 时，门禁只验证披露完整、`aiWatermarkAccepted` 为 `true`、接受方与日期可追溯。

- 每馆配置一个独立封面。雨花台、江上青和扬州带“AI生成/豆包AI生成”水印的现有封面获准原样使用，以 `aiWatermarkPresent`、`aiWatermarkAccepted`、`acceptedBy` 和 `acceptedAt` 透明披露；水印存在本身不得导致内容门禁失败。
- 每馆提供一份 UTF-8 WebVTT，第一行 `WEBVTT`；字幕使用权已经项目方确认，但字幕内容仍须覆盖完整口播、时间轴不重叠倒退，并人工校对人名、地名、年代、数字和标点。
- 渡江带“77周年”横幅的 Hero 获准长期使用；梅园新村牌匾近景获准作为临时 Hero，后续有更合适建筑全貌时可以更换，但当前选择不得阻断发布。所有 Hero 与照片仍需检查裁切焦点、景点归属和画面事实描述。
- 不新增独立的全站背景音乐。视频内已有音乐按项目方已确认的公开展示使用权处理，并随对应视频纳入声明记录。

## 9. 门禁模型

### 9.1 内容门禁

内容门禁必须同时检查三层：

1. **结构层**：恰好八馆、正式名称/ID 唯一、GCJ-02、字段长度、1–5 张照片、恰好一条视频且媒体第一项为视频。
2. **资源层**：英语路径、允许的 CloudBase HTTPS 主机、禁止占位/测试域名、28 张照片及项目侧固定顺序、8 个 Hero、8 条视频、8 个封面、8 份 VTT，以及媒体清单中的版本、类型和 SHA-256。
3. **声明与人工审核层**：逐事实来源覆盖和内容审核继续要求审核人及日期；媒体侧检查项目方公开展示使用权与照片人物肖像许可声明已归档并覆盖对应素材，检查字幕同步和媒体播放验收记录。水印封面不要求“无 AI 水印”，而是要求如实披露；`aiWatermarkPresent: true` 只在缺少项目方接受记录时失败。

离线 CI 不能只凭 URL 非空声称远程对象真实存在。媒体上传后必须由 CloudBase 只读对象清单/元数据与本地发布清单逐项对账，并把对账证据归档；构建门禁验证已核验清单，发布前人工检查真实 HTTPS 访问和浏览器播放。

### 9.2 地图门禁

09B 不提供审图号或地图资源。`src/data/mapCompliance.json` 继续保持：

```json
{
  "status": "blocked",
  "publicUseAllowed": false
}
```

只有实际地图资源名称、权威机构、HTTPS 来源、真实审图号、使用范围、实际资源路径/URL、本地文件 SHA-256（若适用）、核验日期/人员，以及完整疆域、国界、行政边界和岛屿人工检查全部完成，才能另行改为 `verified`。

`status: blocked` 时：

- 公开边界层不得初始化；
- 列表降级仍应可用；
- `npm run check:map` 必须非零；
- GitHub/CloudBase 发布流程必须停止；
- 不得以“仅预览”“已有三个环境变量”或“先上线后补审图号”为由跳过。

## 10. 人工授权节点

以下节点都需要明确人工确认，前一步不自动授权后一步：

1. 用户确认本设计后，才允许创建 09B 实施计划。
2. 内容负责人确认逐事实来源和八馆正式正文后，才允许生成生产 `sites.json`。
3. 项目方已作照片、视频、视频内音乐和字幕公开展示使用权声明，并允许照片中可辨识人物公开展示；后续只归档声明、素材清单和责任追溯，不重新发起许可确认或把它设为阻断节点。
4. 音视频负责人确认重剪/转码和字幕同步方案后，才允许处理 8 条视频和制作/整理 8 份 VTT；该节点只处理技术与内容准确性，不重复审核已经确认的使用权。
5. 用户确认上传清单、目标环境、对象前缀和预计容量后，才允许任何 CloudBase 媒体上传。
6. 用户确认 GitHub 授权、分支、构建命令和目标静态托管实例后，才允许连接自动构建。
7. 地图合规负责人签署并使地图门禁通过后，才允许形成发布候选。
8. `docs/release-checklist.md` 全部完成并由发布负责人确认后，才允许公开发布。

## 11. 失败安全与回滚原则

- 任一权威来源冲突：该字段和该馆保持未审核，生产内容门禁失败。
- 任一媒体格式、字幕同步、事实描述或 URL 未通过：不上传或不切换该对象版本，生产内容门禁失败。已经确认的媒体使用权、肖像许可、渡江 Hero、梅园临时 Hero 及三馆水印封面不得被重新标记为未授权或待确认。
- 项目方许可声明、素材覆盖清单或水印接受记录在数据落地时缺失/不一致：修正记录后再构建；这属于可追溯记录完整性问题，不重新否定项目方已经作出的许可决定。
- CloudBase 只读盘点发现容量、域名、权限或 Git 能力不满足：停止实施，记录缺口，不自动创建替代云资源。
- Git 自动构建失败：保留上一个成功部署，不运行补偿性跳过脚本。
- 地图继续 `blocked`：全站继续禁止公开发布，不伪造审图号。
- 回滚只通过 Git 提交/部署记录与媒体版本 URL 完成；不覆盖原始素材，不在紧急回滚中删除云对象。
